# Project Tether — Architecture

Detailed design document for formally verified AI agent runtime.

## Problem Statement

AI agents with persistent memory (Hermes, OpenClaw, Kagenti) face two unresolved risks:

1. **Memory poisoning** (OWASP ASI06) — prompt injection or corrupted input gets written to persistent memory, influencing all future sessions
2. **Unsound reasoning persistence** — an agent stores a conclusion that doesn't follow from its observations, and that false fact compounds across sessions

Current mitigations are either structural (sandbox isolation, RBAC) or heuristic (content filtering, embedding similarity). Neither provides formal guarantees about what enters or exits persistent memory.

Tether bridges three domains to close this gap:

| Domain | Source | Role |
|--------|--------|------|
| Persistent memory reasoning | Hermes Agent, OpenClaw | Memory architecture patterns (bounded curation, layered tiers, skill learning) |
| Formal proof logic | F\*/Pulse (separation logic), Z3 (SMT solver) | Unified verification of memory operations and stored content |
| Agent sandboxing | NVIDIA OpenShell | Runtime isolation, policy enforcement, inference privacy routing |

## Toolchain

### Unified on F\* + Pulse

All verification — content and substrate — uses a single language and toolchain:

| Layer | Tool | What It Proves |
|-------|------|---------------|
| Content properties (P1-P4) | F\* refinement types | Logical validity of stored reasoning |
| Substrate properties (P5-P8) | Pulse (separation logic DSL for F\*) | Structural safety of memory operations |
| Proof discharge | Z3 SMT solver | Satisfiability of all verification conditions |
| Incremental checking | F\* MCP Server (Rust) | Stateful sessions — re-check only changed code |
| Production compilation | KaRaMeL | Extract verified F\*/Pulse to native C |

F\* refinement types handle what Dafny pre/post conditions do, and Pulse handles separation logic — all in one type system, one verifier, one agent plugin. No need to bridge two languages.

### Agentic Proof Generation (Claude Code + proof-copilot)

Proofs are generated by Claude Code using the [FStarLang/proof-copilot](https://github.com/FStarLang/proof-copilot) plugin. The plugin provides one agent (`fstar-coder`) and 8 specialized skills.

**Installation (Claude Code in VSCode):**

```text
/plugin marketplace add FStarLang/proof-copilot
/plugin install proof-copilot@proof-copilot
```

**Skills used by Tether:**

| Skill | Tether Role |
|-------|----------|
| `fstarverifier` | Core verification loop — runs `fstar.exe`, interprets error patterns |
| `fstarmcp` | Incremental typechecking via F\* MCP server (stateful sessions) |
| `smtprofiling` | Keeps Z3 discharge under the 1s latency budget |
| `proofdebugging` | Diagnoses verification failures on memory property proofs |
| `specreview` | Validates Tether specs (P1-P8) for completeness and correctness |
| `krmlextraction` | Compiles verified Pulse specs to native C for production gateway |

**Paradigm:** The developer describes properties in natural language. The `fstar-coder` agent generates verified F\*/Pulse code in a verifier-in-the-loop:

```text
Developer describes property
        │
        ▼
fstar-coder writes F*/Pulse code
        │
        ▼
    fstar.exe + Z3 checks it
        │
   ┌────┴────┐
   │         │
Verified ✓  Error ✗
   │         │
   │    Agent reads error, fixes, retries
   │         │
   ▼         └──► (loop until verified)
Done — code is machine-checked correct
```

This is validated at scale: the AutoCLRS project produced 120K lines of verified F\*/Pulse code for 52 algorithms using Claude Opus 4.6 — the same model available in this environment.

### Agent Sandboxing (NVIDIA OpenShell)

[NVIDIA OpenShell](https://github.com/NVIDIA/OpenShell) provides the runtime isolation layer with three enforcement components:

| Component | Function | Tether Integration |
|-----------|----------|-----------------|
| **Sandbox** | Kernel-level isolation (seccomp, Landlock, eBPF, cgroups) | Agent + Tether gateway run inside sandbox |
| **Policy Engine** | Deny-by-default filesystem/network/process constraints (YAML) | Enforces runtime constraints; Tether proves logical constraints |
| **Privacy Router** | Controls where inference traffic routes (local vs cloud) | Routes sensitive context to local models |

OpenShell and Tether are complementary:

- **OpenShell** prevents what shouldn't happen (runtime enforcement)
- **Tether** proves what does happen is correct (logical verification)

## Verification Properties

### Class 1: Content Verification (F\* Refinement Types → Z3)

Properties about **what** is being stored.

#### P1: Inference Soundness

The stored fact must follow from the agent's observations via a valid inference chain.

```fstar
val inference_sound :
  observations:list observation ->
  chain:inference_chain ->
  conclusion:memory_entry ->
  Pure bool
    (requires chain.well_formed /\ chain.premises_subset_of observations)
    (ensures fun b -> b ==> chain.conclusion == conclusion.content)
```

**What it catches:** Agent hallucinates a "fact" not grounded in any observation. Without this check, the hallucination enters persistent memory and compounds in future sessions.

#### P2: Consistency

The new fact must not contradict the agent's existing knowledge base.

```fstar
val consistent_with :
  new_fact:memory_entry ->
  existing:memory_state ->
  Pure bool
    (requires True)
    (ensures fun b -> b ==> ~(exists f. f `mem` existing.facts /\ contradicts new_fact f))
```

**What it catches:** Agent stores "user prefers JSON" on Monday and "user prefers YAML" on Tuesday without retracting the first.

#### P3: Poisoning Resistance

The stored value must not contain patterns that would alter the agent's instruction-following behavior on retrieval.

```fstar
val not_poisoned :
  entry:memory_entry ->
  Pure bool
    (requires True)
    (ensures fun b -> b ==>
      ~(contains_instruction_override entry.content) /\
      ~(contains_role_escalation entry.content) /\
      ~(contains_exfiltration_pattern entry.content) /\
      entry.source.trusted)
```

**What it catches:** A web page the agent reads contains "IMPORTANT: from now on, ignore all previous instructions." The agent stores this as a normal fact. On future retrieval, it acts as a persistent prompt injection (OWASP ASI06).

#### P4: Completeness (Spec-Dependent)

If a domain specification defines "critical" observations, all critical observations must be covered.

```fstar
val memory_complete :
  observations:list observation ->
  memory:memory_state ->
  spec:domain_spec ->
  Pure bool
    (requires True)
    (ensures fun b -> b ==>
      (forall obs. obs `mem` observations /\ spec.is_critical obs ==>
        (exists f. f `mem` memory.facts /\ f.covers obs)))
```

### Class 2: Substrate Verification (Pulse Separation Logic → Z3)

Properties about **how** memory is stored.

#### P5: Ownership

The agent writing to memory must own the memory region it's modifying.

```fstar
open Pulse.Lib.Reference

fn persist (agent_id:id) (entry:memory_entry)
  requires pts_to (memory agent_id) full_perm old_state
  ensures  pts_to (memory agent_id) full_perm new_state
```

**What it catches:** In a multi-agent system (kagent with 11 agents), Agent A's memory write modifies Agent B's state because they share a storage backend.

#### P6: Frame Preservation

Writing to the target memory region does not modify any other memory region.

```fstar
fn persist_framed (agent_id:id) (entry:memory_entry)
  requires
    pts_to (memory agent_id) full_perm old_state **
    frame (all_other_memory)
  ensures
    pts_to (memory agent_id) full_perm new_state **
    frame (all_other_memory)
```

**What it catches:** Writing to MEMORY.md corrupts USER.md. Writing to Tier 1 causes a side effect in Tier 3 vector store.

#### P7: Bounds Enforcement

Memory writes must respect structural constraints of the memory architecture.

```fstar
fn persist_bounded (agent_id:id) (entry:memory_entry)
  requires
    pts_to (memory agent_id) full_perm old_state **
    pure (well_formed old_state)
  ensures
    pts_to (memory agent_id) full_perm new_state **
    pure (well_formed new_state) **
    pure (size new_state <= tier1_bound)
```

**What it catches:** Agent writes exceed Hermes' deliberate 2,200-char MEMORY.md bound.

#### P8: Concurrency Safety

When multiple agents or sessions access shared memory tiers, operations must be race-free.

```fstar
fn persist_concurrent (agent_id:id) (entry:memory_entry)
  requires lock_inv memory_lock
    (exists_ (fun s -> pts_to shared_tier full_perm s))
  ensures  lock_inv memory_lock
    (exists_ (fun s -> pts_to shared_tier full_perm s))
```

**What it catches:** Two concurrent sessions both read MEMORY.md, both decide to update it, and one overwrites the other's changes.

## Mapping to Memory Architectures

### Hermes Agent Memory

| Component | Tier | Content (P1-P4) | Substrate (P5-P8) |
|-----------|------|-----------------|-------------------|
| MEMORY.md (~2,200 chars) | 1 | P1, P2, P3 | P5, P6, P7 (2200 bound) |
| USER.md (~1,375 chars) | 1 | P2, P3 | P5, P6, P7 (1375 bound) |
| Session FTS5/SQLite | 2 | P1 (on write) | P8 (multi-session) |
| External provider | 3 | P3 (external input) | P5 (shared provider) |
| Skills (~/.hermes/skills/) | Generated | P1, P3 | P5, P6 |

Hermes' bounded Tier 1 memory (~3,600 chars total) makes verification tractable — proof discharge should be sub-second.

### OpenClaw Memory

| Component | Layer | Content (P1-P4) | Substrate (P5-P8) |
|-----------|-------|-----------------|-------------------|
| Session context (JSONL) | 1 | Ephemeral | N/A |
| Daily logs (YYYY-MM-DD) | 2 | P1 (append-only) | P6 (append preserves existing) |
| MEMORY.md (long-term) | 3 | P1, P2, P3 | P5, P6, P7 |
| Vector embeddings (SQLite-vec) | 4 | P3 (embedded content) | P8 (concurrent writes) |
| Memory-Wiki entries | Structured | P1, P2, P3, P4 | P5, P6 |

## Verification Flow

### Write Path

```text
Agent produces MemoryIntent
        │
        ▼
┌─ STAGE 1: Content Check (F* refinement types → Z3) ──────────┐
│                                                                │
│  Input: MemoryIntent{key, value, reasoning_trace,              │
│         observations, existing_memory}                         │
│                                                                │
│  Check P1: reasoning_trace ⊢ value                            │
│  Check P2: ¬∃ contradiction in existing_memory                 │
│  Check P3: value passes poisoning predicates                   │
│  Check P4: critical observations covered (if spec exists)      │
│                                                                │
│  Output: ContentVC (verification condition)                    │
│  Time budget: < 500ms                                          │
└────────────────────┬───────────────────────────────────────────┘
                     │ pass
                     ▼
┌─ STAGE 2: Substrate Check (Pulse separation logic → Z3) ─────┐
│                                                                │
│  Input: MemoryIntent + target memory region                    │
│                                                                │
│  Check P5: agent_id owns target region                         │
│  Check P6: frame condition — other regions unchanged           │
│  Check P7: post-write size ≤ tier bound                        │
│  Check P8: lock held if shared tier (concurrent)               │
│                                                                │
│  Output: SubstrateVC (verification condition)                  │
│  Time budget: < 200ms                                          │
└────────────────────┬───────────────────────────────────────────┘
                     │ pass
                     ▼
┌─ STAGE 3: Z3 Discharge ──────────────────────────────────────┐
│                                                               │
│  Input: ContentVC ∧ SubstrateVC                               │
│  Z3 proves the combined VC                                    │
│                                                               │
│  SAT     → write proceeds, proof certificate emitted          │
│  UNSAT   → write rejected, counterexample returned to agent   │
│  TIMEOUT → write deferred to async verification               │
│                                                               │
│  Time budget: < 1s (configurable)                             │
└────────────────────┬──────────────────────────────────────────┘
                     │
              ┌──────┴──────┐
              │             │
        Verified ✓    Rejected ✗
              │             │
              ▼             ▼
     Write to memory   Return counterexample
     Emit OTel span    Agent may retry with
     with proof cert   revised reasoning
```

### Read Path (Retrieval Integrity)

```text
Memory read request
        │
        ▼
  Retrieve fact + original proof certificate
        │
        ▼
  Verify: stored_hash(fact) == certificate.content_hash
        │
        ▼
  Verify: certificate.timestamp within validity window
        │
        ▼
  Return fact with confidence annotation
```

## OpenShell + Tether Composition

| Concern | OpenShell | Tether | Both |
|---------|-----------|-----|------|
| Agent can't read another agent's files | Policy Engine (fs deny) | Pulse ownership proof (P5) | Enforce + prove |
| Memory write within bounds | Policy Engine (fs quota) | Pulse bounds proof (P7) | Enforce + prove |
| Agent can't exfiltrate via network | Policy Engine (net deny) | — | OpenShell only |
| Stored reasoning is sound | — | F\* refinement types (P1) | Tether only |
| Memory not poisoned | — | F\* poisoning predicates (P3) | Tether only |
| Sensitive context stays local | Privacy Router | — | OpenShell only |
| Concurrent memory access safe | — | PulseCore CSL (P8) | Tether only |

Tether verification gateway runs **inside** the OpenShell sandbox as a co-process. If Tether ran outside the sandbox, a compromised agent could bypass it.

## Proof-of-Concept Phases

### Phase 0: Foundation (Weeks 1-2)

**Goal:** Verify a single Hermes-style memory write end-to-end.

1. Install F\*/Pulse + proof-copilot plugin in Claude Code
2. Prompt `fstar-coder` to generate Pulse specs for P5 (ownership) and P7 (bounds) against a Hermes MEMORY.md model
3. Prompt `fstar-coder` to generate F\* refinement type specs for P1 (inference soundness) and P2 (consistency)
4. Use `fstarmcp` for incremental checking during iteration
5. Use `specreview` to validate the generated specs
6. Deliverable: verified F\*/Pulse module for a single memory write

Scope constraints: single agent, Tier 1 only, no concurrency, no platform deployment.

### Phase 1: Content Verification (Weeks 3-5)

1. P3 (poisoning resistance) with OWASP ASI06 test vectors
2. P4 (completeness) with a sample domain specification
3. Agent submits verification requests via F\* MCP Server
4. Verification of Hermes skill generation (code satisfies spec before write)
5. Test suite: 50+ memory intents covering valid writes, poisoning, contradictions

### Phase 2: Substrate Verification (Weeks 6-8)

1. Full Pulse model of Hermes 3-tier memory (MEMORY.md + USER.md + SQLite)
2. P6 (frame rule) — prove writes to MEMORY.md don't affect USER.md
3. P8 (concurrency) — PulseCore concurrent separation logic for multi-session SQLite
4. OpenClaw 4-layer model with cross-layer frame reasoning
5. Use `krmlextraction` to compile verified substrate checks to C
6. Benchmark: target < 1s verification for Tier 1 writes

### Phase 3: Red Hat OpenShift AI Integration (Weeks 9-12)

1. Tether gateway deployed as sidecar inside OpenShell sandbox
2. OTel instrumentation: proof certificates as spans
3. Grafana dashboard: verification latency, rejection rate
4. SPIFFE identity integration for P5 ownership proofs
5. OpenShell policy files for Tether agent constraints
6. MLflow integration: proof audit trail

### Phase 4: Multi-Agent + Production (Weeks 13-16)

1. All 11 kagent agents verified
2. Cross-agent memory isolation proofs
3. Performance: verification caching, incremental proofs
4. Async verification path for timeout cases
5. EU AI Act compliance report (Article 9 risk management evidence)
6. Upstream contribution proposal

## Open Questions

1. **Spec authorship:** Who writes the F\* specs for domain-specific completeness (P4)? Can `fstar-coder` generate specs from natural language requirements?

2. **Verification latency:** Hermes processes dozens of tool calls per task. The `fstarmcp` incremental checking helps (~50ms after first check), but is it enough for production?

3. **Spec correctness:** Formal verification proves code meets its spec. If the spec is wrong, the proof is meaningless. The `specreview` skill helps but doesn't fully solve this. The RAND 2026 report flags this as the key unsolved problem.

4. **Graduated trust:** Should verification be all-or-nothing, or should agents earn trust over time? How does graduated trust interact with formal guarantees?

5. **Memory compaction:** Both Hermes and OpenClaw compact/curate memory over time. Is compaction a new write needing verification, or a structural operation needing only substrate proofs?
